# WeCourse 源码适用性评估

评估日期：2026-10-27。仓库：https://github.com/fenzhiere/WeCourse 。核验版本：`5d62da9655db8f3c11205a0b1c9b432b315b5c28`，master 最新提交日期为 2024-10-04（本次实际拉取结果）。

## 结论

**不建议把当前公开仓库作为“下载后改品牌即可运营”的健身房小程序。** 它可以作为页面、字段和查询逻辑的参考，但公开版本缺失大量核心写入业务。按你的需求继续开发，会涉及排课、约课、课时账户、通知和权限等核心模块，而不是几项小修补。

此前仅根据 README 将其列为源码评估首选过于乐观。本次源码核验推翻了“已有排课扣课闭环，只需补自主预约和通知”的判断。

若作者另行提供完整版本，可以重新评估；本报告不代表对未取得的版本做出判断。不要据此认定作者一定有完整商业版，也未核实其报价。

## 你的需求与评估范围

从上一会话恢复的原始需求：健身房使用；约课、排课、扣课、人员管理；给学员和教练发通知；拿到源码自行修改，使用自己的品牌。

“学员自主约课”作为约课需求的工作假设。尚未确认的规则包括：私教或团课占比、门店数量、预约时扣课还是上课后扣课、取消期限、爽约处理、课包有效期、是否线上支付。以下将它们分为首版建议与可选扩展，不把所有扩展当成你的既定需求。

检查了路由、主要业务控制器与服务、数据模型、小程序相关页面、配置和安装手册；对关键发现运行了隔离验证。未部署微信云环境、未登录真实小程序、未执行手机端验收，不声称其余模块已实测可用。本次是选型与关键代码核验，不是全仓安全审计或增量代码审查。

## 最重要的源码证据

以下路径均相对于 `.research/WeCourse/`。可用固定 commit 在 GitHub 对照。

### 1. 34 处固定报错，不能通过关掉演示模式恢复

在 `cloudfunctions/mcloud/project/lesson/service/admin/` 内检出 34 处“该功能暂不开放”：

| 文件 | 处数 |
|---|---:|
| admin_meet_service.js | 17 |
| admin_news_service.js | 9 |
| admin_user_service.js | 3 |
| admin_mgr_service.js | 5 |

计数口径是固定报错语句出现次数，不等于 34 个独立产品功能。

代表位置：`admin_meet_service.js:52` 的 changeCourse、`:57` 的 joinDayTime、`:81` 的 insertDayTime、`:110` 的 insertMeet、`:141` 的 editMeet、`:258` 的 delJoin、`:331` 的 exportJoinDataExcel。

这些函数直接调用 AppError，没有后续业务实现。前后端 `IS_DEMO` 已为 false；路由的 `#demo` 限制和函数内固定报错是两层不同逻辑。删除报错也不会自动生成缺失的功能。

此外，控制器调用 `getHasDayByMonth` 和 `cancelJoinByTimeMark`，但所检查服务及其继承链没有相应方法。月历和批量取消还存在断开的调用链。

### 2. 通知工具函数不等于通知功能

`cloudfunctions/mcloud/framework/lib/mini_lib.js:33` 提供 sendMiniOnceTempMsg；全仓检索仅发现定义和导出，没有业务调用。未找到 `wx.requestSubscribeMessage` 接入；云函数 config.json 的 openapi 权限清单也未列出订阅消息发送权限；未找到对应提醒定时任务。

需要新增：收件人身份绑定、模板配置、订阅申请、预约/改期/取消事件、课前任务、发送记录、失败处理、重复发送防护，以及取消或改期后使旧提醒失效。现有 helper 捕获异常后仅写日志，不能直接支撑可追踪的通知结果。

“通知各个学员和教练”要区分业务提醒与公告广播。不能承诺任意时刻无限群发微信消息。实际可用模板和订阅条件需用你的 AppID/类目核实；本次尝试访问微信官方订阅文档未成功，因此不对当前平台配额或类目资格作确定结论。站内通知列表可作为基础记录；若重要提醒要求额外渠道，再评估短信或适合员工的通知渠道。

### 3. 可复用代码也需要修复权限问题

**存量问题 A：老师详情可能返回登录凭据字段。**

`service/meet_service.js:77` 的 viewMeet 查询 fields='*' 并返回对象。对应模型包含 MEET_PASSWORD、MEET_TOKEN 和 MEET_TOKEN_TIME。用户侧 `controller/meet_controller.js:190` 不做字段白名单过滤。数据库封装遇到 '*' 直接返回整条数据。

隔离验证用虚构数据确认：密码散列和 token 字段会由服务原样返回。教练登录模块确实把这些字段存于同一模型。若真实记录存在有效 token，风险严重；未在实际云环境验证利用。应把公开资料与登录凭据隔离，并对输出使用明确字段白名单。

**存量问题 B：课时流水查询允许传入其他 userId。**

`controller/meet_controller.js:31` 接收 userId，只有为空时才使用当前用户；该方法未校验管理员/教练角色及数据归属。应把“查看自己的流水”和“授权管理人员查看学员流水”分成明确的权限路径。此项为静态调用链发现，未在线验证。

**存量问题 C：注册审核状态由客户端提供。**

`controller/passport_controller.js:43` 接收 status，`service/passport_service.js:44` 直接持久化。前端 USER_REG_CHECK 默认 false；若以后仅在前端打开注册审核，服务端仍信任传入状态。隔离验证确认可传入正常状态。审核策略应由服务端决定。

这些问题说明“跑通页面”不足以作为上线验收。接手任何完整版也应重新核验，不能假设问题已经修复。

### 4. 授权信息不够明确

仓库没有找到仓库级 LICENSE 文件；云函数 package.json 标记 ISC，但多个源文件头写有 CCMiniCloud Framework 的 ALL RIGHTS RESERVED。README 和安装手册未明确授予整套源码改品牌商用的范围。

这是证据不一致和授权范围未确认，并非断言禁止商用。采购/采用前需作者明确：前端、云函数、框架、图片素材是否均有权交付；是否允许修改品牌并用于自己的健身房；是否限制 AppID、部署数量或门店；是否存在加密文件、续费绑定或外部授权接口。

## 课时规则建议

需要你最终确认“扣课”的含义。若想按实际上课统计消课，建议分开保存可用课时、预约冻结课时和已消耗课时：

1. 买 10 节课：可用 10、冻结 0、已消耗 0。
2. 预约 1 节：可用 9、冻结 1、已消耗 0。
3. 正常上课确认：可用 9、冻结 0、已消耗 1。
4. 规定期限内取消：可用恢复为 10，冻结归零。
5. 逾期取消/爽约：按门店明确规则转为消耗或释放，并记录原因。

这是推荐设计，不是当前 WeCourse 已有能力。现有模型主要是全局课时数和流水，未见完整的独立课包、有效期、冻结账户、履约状态设计。`course_model.js` 的类型注释与枚举含义还有相反之处，接手时应统一定义。

若你明确采用“预约即扣、取消即退”，可以简化首版，但仍必须处理重复请求、并发、取消期限和对账，不要混淆“预约扣除”与“实际完成上课”。

## 是否值得继续投入

**直接使用公开版：不推荐。** 节省的是部分界面和查询代码，关键业务仍需重做，权限修复和授权核实也会增加接手成本。

**向作者索取完整交付评估：可以，但先验收再决定。** 要求在你的测试环境演示：创建教练和学员 → 增加课时 → 排课 → 学员自主预约 → 双方提醒 → 取消退回 → 上课消课 → 流水导出。自主预约和通知若不在完整版本内，应单独列入开发范围。

**重新开发核心：适合你重视源码可控的方向。** 可以保留原生微信小程序＋云开发的技术选择，但它与采用这个截断仓库是两件事。即使参考页面，也应先解决代码复用权利，业务数据与权限建议按实际需求设计。

本次不提供“几天改完”或固定报价：单店/多店、私教/团课、扣课时点、通知渠道尚未确定，且未拿到完整版本，直接估价会产生误导。

## 完整版交付时的最低验收用例

1. 余额不足不能预约；两次并发请求不能透支同一笔课时。
2. 同一个预约重复提交不重复扣课；取消重试不重复退课。
3. 两人竞争最后一个名额时仅一人成功；私教时间冲突不能保存。
4. 已预约课程改期/换教练后，学员课表、教练课表和提醒一致。
5. 通知发送失败不回滚已成功的预约，也不触发再次扣课；失败可见。
6. 学员只能查询自己的余额和流水；教练不能获取其他教练凭据或越权管理。
7. 开启审核后，客户端提交 status=1 也不能跳过服务端审核。
8. 课时流水汇总与余额、预约占用、实际消课一致；导出可核对。
9. 在你自己的 AppID、云环境和品牌配置下工作，不依赖作者的数据库。
