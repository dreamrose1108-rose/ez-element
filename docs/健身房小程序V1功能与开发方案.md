# 健身房小程序 V1 功能与开发方案

版本：讨论稿 v1.0｜日期：2026-10-27

## 1. 目标和已确认范围

为一家健身房开发自有品牌微信小程序，支持私教一对一和多人团课，采用线下收款、管理员录入购课的方式。源码从零开发，不复用 WeCourse 的代码或素材。

品牌：元素领域（Ez Element）。

已确认：单店、私教和团课并存、线下收款、自有品牌、人员管理、排课、预约、课时管理、学员与教练通知。

本方案中的取消期限、预约窗口、课时规则等为建议默认值，尚未由经营者确认。应做成可配置规则，正式试运营前确认；本文件不表示已开发或已部署。

首版成功标准：管理员录入购课后，学员能预约，教练能确认出勤，系统能正确扣退课，双方能查询课表与通知，管理员能对账。

## 2. 产品形式与边界

一个微信小程序，按账号权限展示学员、教练、管理员工作台；同一个人可有多个角色。首版管理功能也放在小程序内，暂不单独开发浏览器管理后台。角色切换只影响界面，实际权限始终由服务端校验。

V1 不包括：在线支付、退款支付接口、多门店、营销分销、优惠券、无限次月卡/年卡、转卡共享卡、教练薪酬提成、硬件闸机、复杂排班优化、自动候补递补、独立 Web 后台。现金退款仍在线下完成，系统记录退课及线下退款凭据。

## 4. 私教和团课如何分别运行

### 私教：先发布教练可用时段，再由学员预约

1. 管理员或教练发布具体日期的可约时段；建议以 30 分钟为时间网格，课程默认 60 分钟。
2. 学员只能使用适用的私教课包预约；课包可限定一名教练或指定教练集合，不能默认任意跨教练通用。
3. 预约成功后该时段容量为 1，冻结对应课时，并出现在双方课表。
4. 教练完成授课后确认到课，系统将冻结课时转为消耗。
5. 团课占用同一个教练的时间，因此私教与团课必须统一做时间冲突检查。

教练可修改未预约的空闲时段；已有预约不能直接删除或覆盖。需要走取消或管理员改期流程。

### 团课：先创建场次，再由多个学员报名

1. 管理员定义课程（如瑜伽、燃脂），再创建具体场次：教练、日期、起止时间、场地、容量和每人扣课数。
2. 学员使用适用团课课包预约，成功占用一个名额并冻结课时。
3. 满员显示不可预约；有人取消后重新开放，不自动候补。
4. 教练按名单逐人确认到课或爽约，分别结算课时；不把整场所有学员自动标记到课。
5. 容量不能改为小于当前有效预约人数；调整教练、时间或场地必须重新检查冲突。

团课最少开班人数不做自动停课规则，先由管理员判断是否停课，避免无人处理的临界场次。

## 5. 预约和取消的建议默认规则

| 规则 | 建议初始值 | 说明 |
|---|---|---|
| 提前可约范围 | 未来 14 天 | 可配置 |
| 预约截止 | 开课前 1 小时 | 私教/团课可以分别设置 |
| 免费取消期限 | 私教提前 12 小时；团课提前 2 小时 | 建议值，需门店确认 |
| 正常取消 | 释放冻结课时与名额 | 重复点击不重复退回 |
| 逾期取消 | 禁止学员自助取消，提示联系门店 | 管理员可选择退回或按规则扣除，必须填原因 |
| 爽约 | 教练标记后按约定扣除 | 必须在开课结束后确认；不靠时间经过自动判爽约 |
| 门店取消课程 | 全额释放冻结课时 | 不按学员违约处理 |
| 课包有效性 | 上课开始时间须在课包有效期内 | 不能靠提前预约绕过到期日 |
| 课包选择 | 仅选适用课包；默认推荐最早到期者 | 展示本次使用哪张课包，服务端再次核验 |
| 预约确认 | 有余额、有名额且无冲突则立即成功 | 首版不增加教练逐单审批 |
| 时间边界 | 使用左闭右开区间 [开始,结束) | 10:00–11:00 与 11:00–12:00 不冲突 |

一个学员不能同时预约重叠的私教或团课；一个教练不能同时教授重叠课程。同一专用场地不可重叠；开放健身区可配置为非独占。

改期首版由管理员操作。单个预约改期必须一次性完成“校验新时段、占用新时段、释放旧时段、调整冻结”，失败时保留原预约。团课整场改期需检查全部已预约学员和课包有效期；有冲突时阻止直接发布，给出需处理名单。

停用学员或教练只阻止新的操作，不删除历史课表和账目。已有未来预约进入待处理清单，不能静默消失。

## 6. 课包、线下收款和课时账

### 课包设计

私教和团课分别建课包，不共用余额。一个学员可有多个课包，每包保存：类型、适用课程/教练、购买课时、赠送课时、有效期、入账时间、实际收款金额与备注。

建议首版每次扣课为正整数，默认 1 节；不引入半节课或不同课程折算。所有扣课数在预约时保存快照，之后修改课程价格不会影响既有预约。

### 线下收款登记

管理员选择学员和课包，录入实际收款金额、收款日期、现金/转账等方式和凭据备注；确认后生成课包与入账流水。金额以分为单位保存，仅管理员可见；首版不承担会计系统或收入确认职责。

线下收款金额与消课数量分别统计，不将“已收款”误称为“已履约收入”。录错通过冲正或有原因的调整处理，不能直接覆盖原始记录。

### 课时变化示例

| 动作 | 可用 | 冻结 | 已消耗 |
|---|---:|---:|---:|
| 购买 10 节 | 10 | 0 | 0 |
| 预约 1 节 | 9 | 1 | 0 |
| 正常上课确认 | 9 | 0 | 1 |

若在上课前正常取消，则由“9 可用、1 冻结”回到“10 可用、0 冻结”，不会生成一次真实消课。

流水类型至少包括：购买入账、赠课、冻结、释放、消课、消课冲正、退课、到期失效、人工调整。每笔记录操作人、业务单号、变动前后余额、原因和时间；已生效流水不物理删除。

课包到期后未使用余额标记为到期不可用，仍保留可追溯记录；不会把已有冻结自动消耗。已预约但延期到有效期之外必须重新检查；取消后如果原包已到期，释放回原包的到期余额，不自动获得新的可用期。门店原因造成该情况可由管理员延期并记日志。

退款时只记录实际线下退款和对应课时退回/作废；有冻结预约的课包先处理预约，禁止直接退掉冻结课时。已消耗课时是否退款由管理员通过有原因的例外操作处理。

## 7. 通知方案

站内消息为首版必须能力，微信订阅消息为可用条件下的外部提醒。不要把发送成功当作用户已经阅读，也不承诺任意广播或无限发送。

| 事件 | 学员 | 教练 |
|---|---|---|
| 预约成功/管理员代约 | 课程、时间、地点、冻结课时 | 新预约及课表变化 |
| 取消/改期/换教练 | 更新内容、课时处理结果 | 更新后的课表 |
| 课前提醒 | 建议提前 2 小时 | 同步提醒 |
| 上课结算 | 消课结果、剩余课时 | 在工作台查看结算状态 |
| 门店公告 | 站内公告 | 站内公告 |

预约时距开课不足 2 小时，成功通知后不再补发重复课前提醒。学员和教练分别绑定自己的微信身份、申请相应订阅。具体模板、用户授权次数及账号类目资格以实际 AppID 可用能力为准。

发送失败或没有可用订阅资格时，保留站内记录并在后台标记需人工联系；短信/企业微信自动发送不纳入首版。

业务事务提交后，通过通知任务异步发送；通知失败不撤销预约、不重复扣课。每个事件/收件人/渠道生成唯一任务键；重试需考虑供应方响应超时造成的结果不确定，不能保证外部渠道绝对只发送一次。改期和取消通过课程版本使旧定时提醒失效。

## 8. 技术方案

建议采用原生微信小程序 + TypeScript、Node.js 云函数、腾讯 CloudBase 文档数据库、云存储和定时任务。一个小程序承载三类角色，减少首版端数和部署工作。具体运行时与依赖版本在项目初始化时按云环境支持情况锁定。

不使用 WeCourse 的自定义框架，从零实现模块清晰的业务代码。前端模块：登录、课表、私教、团课、预约、课包、消息、教练工作台、管理工作台。服务端模块：身份权限、人员、排课、预约、账户流水、出勤、通知、报表与审计。

CloudBase 官方文档说明数据库事务在服务端运行，并有事务操作数量及 doc 操作限制；因此采用确定性文档 ID 和细粒度事务，不能把客户端多次写入当作一个完整交易。[官方事务文档](https://docs.cloudbase.net/database/transaction)

### 核心数据对象

| 对象 | 主要字段/作用 |
|---|---|
| users / roleBindings | 微信身份、学员状态、角色；绑定流程须核实本人，不能凭自填手机号接管既有课包 |
| coachProfiles | 教练介绍、启用状态、可授课程；公开资料不含身份凭据 |
| courseTypes / rooms | 私教/团课类型、时长、扣课数、场地占用规则 |
| sessions | 具体场次、教练、地点、容量、已占名额、状态、规则版本 |
| availability | 教练可约时间；用于生成具体可预约私教时段 |
| memberPackages | 学员课包、适用范围、可用/冻结/消耗/失效、有效期 |
| purchaseRecords | 线下收款与开卡记录、金额、凭据备注、操作人 |
| bookings | 学员、场次、课包、状态、扣课与取消规则快照 |
| creditLedger | 不可覆盖的课时流水、关联预约、冲正关系 |
| scheduleLocks | 学员/教练/场地的日期占用或版本锁，防并发交叉预约 |
| notificationJobs / inbox | 待发送事件、发送结果、站内消息、课前提醒版本 |
| auditLogs / requestKeys | 管理操作记录、请求去重与重试结果 |

### 必须保证的技术规则

1. 所有排课、预约、扣退课、人员角色和金额修改只由服务端执行。客户端不能直接改业务集合。
2. 预约事务同时更新预约记录、场次名额、课包冻结、必要的时间占用和通知事件；失败全部回滚。
3. 同一学员/场次采用确定性业务键；取消后再次预约使用明确的预约版本，保留旧流水。
4. 时间冲突不能仅靠事务外查询。私教占用教练/学员日程锁，团课场次发布时占用教练/场地锁，学员报名只占用个人日程和该场名额。
5. 服务端按固定顺序处理共享日程文档，并对写冲突做有限重试；即使不同场次并发也不能让同一个学员重叠预约。
6. 预约和结课都使用请求幂等键及状态前置条件，重复请求返回同一业务结果。
7. 整场停课采用“先关闭新预约，再分批幂等释放”的任务流程；逐个退回可恢复、可对账。避免人数多时超出单事务限制；未完成时明确显示取消处理中。
8. 结课逐预约结算；批量按钮仅编排这些单笔操作，能显示部分失败并安全重试。
9. 敏感字段白名单输出，教练只看本人授课所需名单；金额、全店流水和权限变更仅管理员可见。
10. 开发/测试与正式环境分离；时刻统一存储，按 Asia/Shanghai 展示与计算门店日期。备份与恢复需经过实际演练。

## 9. 业务状态

场次：草稿 → 可预约 → 进行中 → 已结束；可预约场次可进入取消处理中 → 已取消。结束与结算完成分开，避免时间一到就自动扣课。

预约：已确认/课时冻结 → 已到课/已消课，或已取消/已释放，或爽约/按规则消课。未确认出勤保持待结算并提醒教练。管理员纠错生成冲正事件与新的处理结果，禁止改写原始流水。

管理员改期、取消或调整余额必须记录原因；已开始课程禁止普通用户改期。涉及过往课程由管理员走纠错流程。

## 10. 开发顺序与交付阶段

以下为计划量级估算，不是承诺工期。假设一名熟悉微信小程序与云开发的全栈开发者投入，需求变化较小，门店可及时验收；不含账号申请、平台审核等待和额外渠道采购。

| 阶段 | 交付物 | 估算工作日 |
|---|---|---:|
| 1. 规则与原型 | 页面结构、操作流程、权限表、规则确认、数据模型 | 2–3 |
| 2. 基础与账户 | 登录、角色、人员、课包、线下入账、流水 | 4–6 |
| 3. 排课与预约 | 私教时段、团课场次、自助预约、代约、取消、并发控制 | 6–9 |
| 4. 履约与运营 | 出勤消课、纠错、改期/停课、通知、统计导出 | 5–8 |
| 5. 测试与试运营 | 并发/权限/账目测试、真机测试、备份恢复、门店试用修正 | 4–6 |
| 合计 | 可试运营首版 | 21–32 |

预计约 4–7 个工作周。可以较早交付可点击原型和演示版，但不能把演示完成当作课时账与通知已经可运营。正式排期在第 1 阶段后收敛。

交付包括：前后端源码、依赖锁文件、数据库结构及索引说明、部署脚本/步骤、配置清单、测试记录、管理员手册、备份恢复步骤。账号与云资源归门店持有，代码进入你控制的仓库。

## 11. 首版验收标准

1. 私教：教练发布时段 → 学员购课入账 → 预约 → 查看双方课表 → 结课扣除，全流程完成。
2. 团课：发布 10 人场次，11 人并发抢约时最多 10 人成功；失败者不冻结课时。
3. 同一学员并发预约重叠课程，最多一个成功；教练私教/团课不能重叠排期。
4. 只剩 1 节课时同时发起多笔预约，不能产生负余额或多冻结。
5. 重复提交预约、取消、结课和退款登记，不重复扣退课、不重复记录收款。
6. 取消截止边界、开课边界、课包到期边界行为与配置一致。
7. 私教课包不能预约团课，不适用教练/课程和过期课包不能使用。
8. 停课时所有未消耗预约最终释放；任务中断可恢复，课时和名单一致。
9. 改期失败保留原预约；改期成功后旧提醒不再发送。
10. 通知拒绝订阅、发送失败和超时不影响预约成功及账户正确性；站内记录可见。
11. 学员不能查看他人流水，教练不能调整课包或读取收款金额，公开详情无凭据字段。
12. 开启审核后伪造客户端状态不能自动通过，绑定手机号不能夺取他人账号或课包。
13. 购课、赠课、冻结、释放、消课、冲正、退课和到期后，余额均能用流水重建核对。
